## 2026-11-09（1.3.12）zip 导入 / 失败不丢旧数据 / 检查单分享 / 留白

### 导入 zip 为什么必然失败

文件选择器那条路径（`importFiles`）对每个 Uri 都调 `importer.stream(uri)`，也就是按
UTF-8 文本读。`.zip` 是二进制，读出来是乱码，网页侧 `NavParser.parse` 自然什么都拿不到，
最后只能回一句 `notifyApplied(false, '数据不可用')` —— 用户看到的就是「数据未生效：数据不可用」。

「选文件夹」那条路径一直是好的，因为它走的是 `streamZip`。所以这次不是修解压逻辑，
而是**把压缩包分流接上**：

```kotlin
if (DataFolder.roleOf(name) == DataRole.ZIP) {
    importer.streamZip(uri, acceptFor(kind)) { ... }
} else {
    importer.stream(uri) { ... }
}
```

`acceptFor(kind)` 与文件夹路径共用 `DataFolder.roleOf`，免得同一个文件在两条入口下
得到不同待遇。`streamZip` 的返回值从 `List<String>` 改成 `ZipScan(names, truncated)`：
被体积上限截断时，失败提示里要能说清「是截断，不是数据坏了」。

### 导入失败为什么会丢掉旧数据

链路上有两处「先破坏、后验证」：

1. `importer.remember(uris)` 在导入**开始**时就写偏好。导一份坏数据，上次能用的那批
   Uri / 文件夹就被顶掉了，下次启动按坏记录重导又是一次失败。
   → 改成 `pendingRemember`，等 `onDataApplied` 回 `ok` 才提交。
2. 网页侧数据被换掉后 App 不会补救。
   → 但**不能无条件重放缓存**：重放会走 `UI.applyData` 里的 `resetSelection()`，
   把用户刚生成好的航路和选好的机场一起清掉 —— 数据没丢的情况下这是纯破坏。

怎么判断页面里的数据到底换没换：`onDataApplied` 的 payload 里带 `info: datasetInfo()`，
它是**当前** `window.__DATASET__` 的规模。拿它和上一次成功生效的规模比，一致就说明
`applyData` 在提交前就失败了（它是先校验再提交的），页面没被改动；不一致才用缓存恢复。

### 检查单分享

`CustomChecklistStore` 新增 `exportJson()` / `importJson()`。导出带一层信封
（`kind` / `version` / `exportedAt` / `checklists`）；导入三种形态都认：带信封的对象、
裸数组、单个对象 —— 别人手工整理的文件不该因为少了几个外层字段就被拒之门外。

**导入必须重新发 id 与 uid**：沿用对方的 id 会和自己已有的副本撞（同一 id 只能存一份），
沿用 uid 会让两份副本共用同一份勾选进度。

自定义检查单分区改成**始终显示**：原来 `if (customs.isNotEmpty())` 才渲染，
一份都没有时连「导入」入口都不存在，第一次用的人没有地方放文件进来。

### 留白

`EfbApp` 外层 Scaffold 按 `systemBars` 留白，内层各页的 Scaffold **又**留了一次，
两行顶栏还额外 `.statusBarsPadding()` —— 三处叠加，标题离刘海远出一条状态栏，
列表底边离底栏也高出一截。

改法：内层 `Scaffold` 统一 `contentWindowInsets = WindowInsets(0)`，
`TopAppBar` 统一 `windowInsets = WindowInsets(0)`，`TwoLineTopBar` 去掉 `statusBarsPadding()`。
`OnboardingScreen` 不在 `EfbApp` 里，自己的留白保持原样，没动。

1. **`JSONTokener` 对垃圾输入不抛异常**。随便一段中文它也能解析成一个 String 值，

## 2026-11-09（1.3.11）日志落盘 / 崩溃捕获 / 航路结果丢失

### 原来的问题

1. **出问题没有任何证据**。全工程只有 `android.util.Log`，日志只活在 logcat 的环形缓冲里。
   用户反馈只能是「它突然没了」，既拿不出堆栈，也说不清操作顺序。
2. **异常处理有两类漏洞**：
   - 会把应用带崩的：`MainActivity.requestStorageAccess()` 最后一行是 `throw`，
     而它是按钮回调 → 点一下就闪退；`ChartViewModel` 的搜索 / 机场列表 / 打开机场
     三个协程包着数据库查询，索引被换掉后查询会抛 `IllegalStateException` → 输一个字就崩；
     `ToolsBridge` 里 `main.post {}` 的 Runnable 也是裸的。
   - 静默吞掉的：数据集缓存写盘失败、航路库 / 选中分组 / 自定义检查单的 JSON 解析失败，
     全是 `runCatching {}.getOrNull()`，出了问题日志里一个字都没有。
3. **工具页切子页丢结果**：生成完航路 → 切到油量计算器 → 切回来，航路回到初始占位。

### 日志设施

`com.oguricap.efb.diag` 三个文件，职责分开：

| 文件 | 职责 |
|---|---|
| `AppLog` | 分级日志、后台单线程写盘、按体积轮转、`flush()` 屏障、清空与统计 |
| `CrashGuard` | `setDefaultUncaughtExceptionHandler`，同步写崩溃文件，保留最近 5 份 |
| `LogExporter` | 拼报告（环境头 + 崩溃 + 日志），写进用户选定的 Uri |

几个设计上的取舍：

- **调用线程只格式化，不写盘**。日志调用点大量在主线程（Compose 的 `update`、桥回调），
  同步写会被 StrictMode 记一条主线程磁盘 IO。格式化（含堆栈）在调用线程做完，
  追加与轮转都排到 `efb-log` 单线程 executor 上。
- **每条都 flush**。进程被杀时缓冲区里的内容就没了，而日志最有价值的时刻恰好是崩溃前那几行；
  崩溃路径另外调 `AppLog.flush()` 等排队条目全部落地，超时 3 秒。
- **轮转按体积不按日期**。单文件 512 KB、2 个归档，总量约 1.5 MB。
  轮转靠改名，导出时「归档序号从大到小 → 当前文件」拼起来就是时间顺序。
- **不做自动重启**。崩溃记录完把异常交回原 handler，让系统按正常流程结束进程。
  重启循环远比重启失败更难排查，也可能在飞行中反复打断操作。
- **崩溃文件名带毫秒**（`crash-yyyyMMdd-HHmmss-SSS.txt`）。只到秒的话，
  同一秒内的两次崩溃会互相覆盖，把第一现场盖掉；字典序仍然等于时间顺序，裁剪与导出都依赖这一点。
- **未 `init` 时降级成只进 logcat**。日志设施本身不能成为新的故障源。

导出走 `ActivityResultContracts.CreateDocument("text/plain")`：位置由系统选择器给出，
内部存储 / SD 卡 / 网盘都行。写入用 `"wt"` 而不是 `"w"` —— 用户可能选中一个已存在的同名文件，
只写不截断的话旧内容会留在尾部。

### 异常处理

- `requestStorageAccess()` 去掉 `throw`，改成记日志 + `pickFailure` 提示。
- `ChartViewModel` 三处数据库协程改成 `runCatching` + `loadError` 提示。
- `ToolsBridge` 所有 `main.post {}` 收进 `postToMain(name) { }`：`try/catch` + 记日志 +
  一句「页面回调出错，本次操作可能没生效」。提示不拼异常原文，细节留在日志里。
- `ToolsWebView` 补 `onRenderProcessGone`（返回 `true` 阻止系统连应用一起杀，并重建该页）、
  `onReceivedError`（只把主文档失败当故障）。
- `DatasetCache.write()` 改成返回 `Boolean`，失败时由 ViewModel 提示「下次需重新解析」。
- 规范文档导出先判 `isDirectory` 再 `mkdirs()`。

### 航路结果为什么会丢

`ToolWebRuntime` 原来是「换孩子」：`removeView(旧) + addView(新)`。这一版为了修
「工具页点不动」（1.3.1）才这么改的，触摸是对的，但把 WebView 摘出窗口再挂回去，
`loadDataWithBaseURL` 的页面会被重新装载。

页面的导航数据之所以「看起来还在」，是因为 `maybeAutoRestore()` 在 `onPageFinished` 里
从本机缓存把数据集补了回来；而生成好的航路是用户临时算出来的 DOM 状态，没有落盘，
于是只剩它消失 —— 正好对上「切到油量计算器再回来，航路没了」。

现在：两个 WebView 都留在同一个 FrameLayout 里，切页只改 `visibility`（GONE）。
不摘视图，就不会有摘下/挂回；GONE 的子视图不参与布局也不参与命中测试，
所以不会重演 1.3.1 的「上层宿主吃掉触摸」—— 那个坑的成因是**两个 AndroidView 宿主叠在 Box 里**，
现在是**一个宿主里的两个子视图**，前提不同。

另外给每个子页加了装载次数统计：同一实例装载第二次会记一条 warning，
以后这类问题在导出日志里一眼能看出来。

### 检查单

- 自定义检查单从 `groupBy { it.category }` 里过滤出来，单独成区放最上面
  （它们是用户自己复制/改过的，用到的概率远高于内置机型，混在「其他」里每次都要往下翻）。
- 「自定义检查单」「随附手册」共用 `SectionRow`：整行可点、带箭头、可收起，
  状态用 `rememberSaveable` 保持。
- `ChecklistRow` 上下内边距 2dp → 8dp，并 `heightIn(min = 48.dp)`；
  `AircraftRow` 12dp → 14dp。

### 踩到的坑

1. **`logEnabled` 的私有 setter 和 `setLogEnabled()` 撞 JVM 签名**，编译期报
   `Platform declaration clash: setLogEnabled(Z)V`。和 1.3.3 那个「属性与方法同名导致
   递归空转」是同一类问题的另一种表现。改名 `applyLogEnabled()`，与 `applyInvert()` 一致。
2. **`runCatching` 包住整个协程体会把 `CancellationException` 当成真失败**。
   `searchJob?.cancel()` 之后，旧协程的 `withContext` 抛取消，被 `onFailure` 接住后
   写进 `loadError` —— 表现就是「每敲一个字都可能闪一下索引读取失败」。
   改法：`runCatching` 只包查询本身，`exceptionOrNull() is CancellationException` 直接返回。
3. **`ShadowContentResolver.registerOutputStream` 在 4.16 里是实例方法**，不是静态的。
   要用 `Shadows.shadowOf(context.contentResolver).registerOutputStream(uri, sink)`。
4. **`WebResourceError.getDescription()` 返回 `CharSequence`**，直接 `?: "..."` 得到的
   仍是 `CharSequence`，传给要 `String` 的函数会编译失败；补 `.toString()`。

## 2026-11-09（1.3.9）修航路 → 油量的航程联动

### 现象

「航路规划的航程无法正常被油量计算器读取」——生成完方案切到油量页，航段距离没被填进去
（或填的是上一次的数字）。

### 定位

用无头 Edge 量了整条链路的时序（真实 2611 数据，ZBAA→ZSPD）：

```
方案卡片出现在 DOM      2342 ms
shim 通知 Kotlin 刷新    2713 ms   ← MutationObserver 400ms 防抖
```

中间的 ~370 ms 是空窗：**卡片已经能看见，但 ViewModel 里的快照还是上一批（甚至空的）**。
用户在这段时间切到油量页，`currentDistNM()` 拿到 null，`fillFuelDistance()` 直接 return，
而且**之后再没有任何时机重试** —— 这条链就此断掉。

顺带查出两处会放大问题的地方：

1. `distanceJs` 无论有没有写进 `#dist` 都 `return true`，失败也是"成功"，日志里看不出来；
2. `currentDistNM()` 优先用航路库里「设为当前」的记录，界面上却只显示一个数字，
   用户看不出这个距离到底来自新方案还是旧航路。

### 改了什么

| 位置 | 改动 |
|---|---|
| `selectPage(Fuel)` | 不再直接填，先 `refreshPlans()` 重读一次 DOM，读完再填（`pendingFuelFill`） |
| `refreshPlans()` | 读完后若在油量页、还没填成功、且仍在切页后 5s 窗口内 → 补填（迟到的方案也能补上） |
| `distanceJs` | 返回 `String(el.value) === v`，只有字段真的写进去才算成功 |
| `fillFuelDistance()` | 失败先 300 ms 重试一次，再失败就弹提示，不再静默 |
| 底部条 | 显示距离来源：`当前航路 673 NM · 当前方案` / `· 航路库 · 北京-上海` |
| 「重新填入」 | 不再因「没有航程」置灰（点了没反应的按钮最容易被当成坏了），改为点了给解释 |
| `refillFuelDistance()` | 新增：没有航程时提示「先在航路页生成一次，或在航路库里设为当前」 |

5s 窗口是刻意收窄的：过了这个窗口说明用户已经在看油量页，再改他手输的距离就是打扰。

### 验证

## 2026-11-09（1.3.7）选文件夹自动识别 + AIP 不再清空机场

### 起因：用户「把 AIP 导进去之后算不了」

先按用户的怀疑（第二份数据冲突）复现：用真实的 `xplane12-native-2611-r1` 导航包 + 用户提供的
`2611V2.zip`（CAAC 四张 CSV + 四张 PDF），在无头 Edge 里跑完整的 App 管线
（`efb_shim.js` + 192K 分块 + `importCommit` + 缓存回传/恢复）：

```
NAV  机场 16698 / 节点 47275 / 航段 90345
AIP  航路 1952 条 / 覆盖机场 486 个 / 国内走廊 1804 条
GEN  ZBAA→ZSPD 5 案（最优 670 NM）· ZBAA→KJFK 9 案（最优 6950 NM）
RESTORE 后重算 5 案
```

**结论：AIP 和导航数据不冲突**，两者是叠加关系；AIP 只改 `caac / domestic / priority`，
数据集（nodes/segments/airports）原样保留。

真正的两个坑：

1. **少了 `earth_aptmeta.dat` 就没有机场坐标。** XP12 的导航包里**没有 apt.dat**
   （apt.dat 在 Global Scenery 下），机场坐标全在 `earth_aptmeta.dat` 里。
   而页面自带的说明表把 aptmeta 写成「本工具用不到，拖进来会标成不需要」——照着选三个文件，
   结果 `airports = 0`：输入 ZBAA 报「数据库里没有 ZBAA」，生成按钮永远是灰的。
   对照实验（只导 fix/awy/nav）复现出这个状态，和用户描述完全一致。

2. **AIP 应用会走页面的 `resetSelection()`。** `UI.applyData()` 结尾无条件清空起降机场、
   置灰「生成航路」。换导航数据时这是对的，但 AIP 只是加一层官方航路 ——
   用户刚选好的机场被清掉，看起来就是「导完 AIP 不能算了」。

3. 附带：AIP 入口没有挑文件类型。CAAC 压缩包里同时有 PDF 报表，一起选中会得到四条
   「表头里没有 Fly along 列」的告警；只选 PDF 时甚至"导入成功"但官方航路 0 条。

### 改了什么

**① 工具页新增「选择数据文件夹」（推荐入口）**

- 网页里由 shim 注入两个按钮（导航 / AIP 各一个），点击调 `Android.pickFolder(kind)`
- App 用 `OpenDocumentTree` 选目录，`DataFolder.scan()` 递归列目录（深度 ≤ 6、文件 ≤ 4000）
- 按**文件名**定角色：`earth_fix` / `earth_awy` / `earth_nav` / `earth_aptmeta` / `apt.dat`，
  其余（CIFP、airspaces、hold/mora/msa、PDF）静默忽略
- 同角色多份时 `Custom Data` 优先、`default data` 最后
- 目录里只有 `.zip` 时，App 侧用 `ZipInputStream` 顺序解压，边解边按 192K 字符送进网页 ——
  网页那条管线是纯文本的，二进制塞进去只会变乱码
- 一个目录里同时有导航数据和 AIP 表时：先导导航，等 `onDataApplied` 回执再导 AIP
  （AIP 要用新数据集的坐标重建走廊，两个 `importCommit` 连着发会读到旧数据集）

**② AIP 入口**

- 保留起降机场：`finishApply(..., keepSelection)` 在 `applyData` 前后存取 `#fromInput/#toInput`，
  应用完再填回去并派发 `input`，页面自己的校验会把「生成航路」重新点亮

- 一条航路都没解析出来时不再报"成功"，而是把 `AipParser` 的告警原样抛给用户

**③ 导入记录与自动恢复**

- `remember()` 从**合并**改成**整批覆盖**：旧的周期文件留在列表里，缓存失效时会被一起重导，

- 新增 `rememberTree()`：记住文件夹 Uri；缓存缺失时按文件夹重扫，而不是重放一串散文件
- 文件夹与散文件两种记忆互斥（记一个清另一个）

**④ 提示语**

- 机场为 0：「已导入但没有机场坐标……否则输入 ZBAA 会提示数据库里没有」
- 航段为 0：「检查是否漏了 earth_awy.dat」
- 用 aptmeta 补上坐标后，过滤掉页面那句误报的「没有 apt.dat —— 机场列表为空」

### 1.3.1 工具页点不动

**现象**：航路页能正常渲染，但点击毫无反应（油量页反而正常）。

**排查**：把打过补丁的 HTML 丢进无头 Edge 跑探针：

```
PROBE|EFB=yes|UI=object|NavParser=object|CLICK=BOUND
```

`CLICK=BOUND` 说明事件绑定正常 → 排除 HTML / 补丁 → 锁定在 Android 视图层。

**根因**：两个 `ToolsWebView` 并排放进同一个 `Box`，靠 `View.INVISIBLE` 切换。
Compose 的 `AndroidView` 外层是 `AndroidViewHolder`（ViewGroup），**宿主本身始终可见、始终参与命中测试**，
上层那个即使内部 WebView 不可见，也会先吃掉所有点击 → 下层航路页收不到触摸。

**修法**：改成一个 `FrameLayout` 宿主，同一时刻只把当前子页的 WebView 挂进去。
未挂载的实例仍然活着（JS 上下文、已导入数据、滚动位置都在），切回来只是 `addView`。

**附带修**：`detachChannel` 是按引用比对的，原来 `destroyAll` 传一个新建的空 channel 不会命中，
会留下指向已销毁 WebView 的悬挂通道。改成用创建时那一份。

### 1.3.3 同名递归

**现象**：1.3.2 装上后点「选择文件」仍然不弹。

**根因**（反编译坐实）：

```kotlin
private val pickNavFiles = onPickNavFiles        // 回调属性
@JavascriptInterface
fun pickNavFiles() { main.post { pickNavFiles() } }   // 桥方法
```

Kotlin 的 `foo()` **优先匹配成员函数**而不是同名属性的 `invoke()`，于是投递的是一个「再次调用自己」的
Runnable —— 每次点击都在主线程排队一个新任务，无限空转，回调一次都没执行。

```
private static final void pickNavFiles$lambda$0(ToolsBridge);
   1: invokevirtual  // Method pickNavFiles:()V     ← 调的是自己
```

编译零警告、不崩溃、100 个单测全过，只有反编译才看得见。修法：属性改名 `onPickRequest`。

**规范**：桥类里「构造参数 → 私有字段」一律用 `onXxx` 前缀，绝不能与 `@JavascriptInterface` 方法同名。

**三个导入入口**：`#fileNav` / `#fileAip` / `#filePack` 一次性全钩上，桥改成 `pickFiles(kind)`，
`importCommit()` 按 `nav` / `aip` / `pack` 分派。`applyAip` 用 `lastPack` 当 pack（页面内部 `current` 外部拿不到），
`ctxCaac` / `ctxPriority` 跨次记住，避免导数据包把 CAAC 表冲掉。

门禁 `requiredConsts` 增加 `AipParser`（8 个）。

### 1.3.6 深色配色 + 胶囊 + 自动读取 + 移除 QRH + 数据持久化

**① 整体深色**
`Theme.kt` 直接采用航路生成器页面的 `:root` 配色（`#0f141a` / `#1a212b` / `#4a9eff` …），固定深色不跟随系统 ——
工具页里嵌的是硬编码深色的网页，App 若在浅色模式给白底，切进工具页会像换了个应用。系统栏同时改为深色样式。

**② 工具页底部操作条删除**
「导入导航数据」和「读取方案」两个按钮都拿掉了：
- 导入改走网页自己的「数据管理」（三个入口都已接通）
- 读取方案改为自动

**③ 方案自动读取**
shim 用 `MutationObserver` 盯住 `#results`，稳定 400ms 后调 `Android.onPlansChanged()`；
Kotlin 侧 `refreshPlans()` 加了 `plansDirty` 补偿：正在读的时候页面又变了，读完补读一次，
避免「读完的瞬间正好生成完」漏掉。内容没变就不写 state，防止整页重组。

用观察器而不是定时轮询：页面空闲时零开销。

**④ 保存 / 航路库 → 可展开胶囊**
右下角一颗 FAB，展开后浮出「保存当前方案」「航路库 (n)」两颗扩展按钮，点空白处收起。
放底部条会把网页的结果区挤到看不见的地方。

**⑤ 移除 QRH 标签**
底部只剩「航图 / 检查单 / 航路·油量」。`QrhScreen`、`QrhSectionScreen` 与 `qrh.json` 保留在仓库里
（功能代码与数据都还在），只是界面入口摘掉了，将来要恢复成本很低。

**⑥ 导航数据持久化（本轮重点）**

原来只记 SAF Uri，每次进工具页重解析 25 MB —— 用户体感就是「每次都要重新导入」，
而且 Uri 授权一旦失效就直接解析失败。

改成：

```
导入成功 → 网页把编码好的 pack 分块回传（packBegin/packChunk/packDone，每块 180K 字符）
        → App 写进 filesDir/efb_dataset_cache.json（先写 .tmp 再 rename）
下次启动 → 读缓存 → 走和数据包导入相同的分块通道（kind=restore）→ 直接应用
换数据   → 再导一次，整份覆盖
```

- 缓存是**应用私有目录**，不进 APK、不进仓库、其它应用读不到
- 回传分块是因为整份 pack 有几 MB，一次性从 `evaluateJavascript` 返回会撞 Binder 上限
- `restore` 不复写缓存（`files[0].fromCache = true`），避免每次启动白写几十兆
- 缓存读不出来时自动退回「按记住的 Uri 重新解析」，双保险

实测（无头浏览器）：合成 pack 导出 1 次 → 缓存 203 字符、含 NODES/SEGMENTS/AIRPORTS/caac/priority →
`restore` 后节点 2 / 航段 1 / 机场 1，且 `packBegin` 只调用 1 次（没有回写）。
